1. **PDF 每行一页**：夹具首版把每行渲染成独立一页，造出 4 页的"报告"。这与真实形态
   不符，也让"页内行序"类断言失去意义（每页只有一行，行序永远对）→ 改为**单页多行**。
2. **列坐标写死导致单位挤进下一列**：渲染器首版用固定列距，而 `10^9/L` 比 `U/L`
   宽一倍 → OCR 把"单位 + 区间"读成一串。改为**按各列最宽内容实算列起点**。
3. **笔画字体的 `9` 字形上下颠倒**：把碗画在下半部，于是渲染出来的是 `6`——OCR
   稳定读成 `6`（这正是"读数错了"而非"读不出来"）。逐字形 A/B 后修正。
4. **空格判定基准选错**：首版用"相邻碎片间距的中位数"，在两三个碎片的行上退化成
   "间距 = 它自己"，阈值被抬到判不出空格（`U/L` 粘成 `U/L`）；改用**字符均宽**基准
   （不受个别字形抖动支配）后，三种形态都得到正确行。
5. **降质强度不够决定性**：首版噪声强度下有 1 行分值 0.8087 > 0.8 阈值，"未复核零落库"
   的断言会变成"有 3 行低了"的弱断言 → 强度扫到 6400，使**每行**都低于阈值。

**M2 的字体渲染局限（如实登记）**：自写笔画字体在 4×6 字形盒里，**次方符号（`^`）
与波浪线区分度不足**——实测 OCR 会把它读成 `~` 或 `>`。故扫描件夹具**刻意避开含
次方符号的单位写法**（选 `umol/L`/`mmol/L`/`U/L` 等），覆盖同样多的路径而读数可靠。
这是**夹具渲染器的局限，不是 OCR 引擎缺陷**（真实字体下 `10^9/L` 读数正常，
见"真实 OCR 通道"一行的实测）。

1. **首启免责在真实入口永不触发**：`main()` 从 `python -m` / 裸 console script 进来时

8. **测试污染开发者真实主目录**：`ledger`/`export`/`report` 经 `main()` 触发首启免责，

## 数字承诺纪律

不写会随实现漂移的硬数字（测试数/用例数/条目数）；真值覆盖度门槛按"指标域/异常类型列最低覆盖项"写进基准 manifest，以末态回填。**本文档中出现的 399/64/37/64/12 等数字均为收尾当轮实测，非抄写。**
